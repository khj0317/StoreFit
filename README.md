# StoreFit

대학생·1인 가구를 위한 **짐 보관 예약 플랫폼**입니다. 이용자는 스토어핏 정식 지점을 골라 예약·결제하고, 지점 사장님은 QR을 스캔해 짐을 받고 돌려줍니다. 본사 관리자는 지점을 등록하고 운영 신청을 심사합니다.

기획부터 백엔드·프론트엔드·결제·문자 알림·배포 준비까지 혼자 진행한 프로젝트입니다.

![홈](docs/screenshots/00-home.jpg)

## 주요 기능

**이용자**
- **휴대폰 인증 가입** — 인증번호 발송·확인 후 일회용 토큰으로 가입. 아이디 찾기·비밀번호 재설정·번호 변경도 같은 인증을 쓴다
- **지점 예약** — 날짜를 고르면 지점마다 그 기간에 남은 자리를 보여주고(카카오 지도 + 목록), 짐 종류·개수·기간으로 요금 자동 계산
- **결제와 체크인 QR** — 결제가 끝나면 체크인 QR(+8자리 코드) 발급. 예약 후 30분 안에 결제하지 않으면 자동 취소
- **취소·환불** — 시작 전날까지 전액, 시작일부터 50% 부분 환불
- **문자·카카오 알림톡** — 예약 확정, 체크인·체크아웃, 찾는 날 하루 전, 연체, 환불, 자동 취소, 노쇼

**지점 사장님**
- **정식 지점 운영 신청** — 본사가 등록한 지점 중에서 신청하고, 승인되면 운영 시작
- **QR 체크인/체크아웃** — 카메라로 QR을 스캔하거나 코드를 입력하면 예약 내용을 먼저 보여주고, 확인을 누르면 처리
- **운영 대시보드** — 오늘 입고·출고 예정, 보관 중인 짐, 이번 달 매출, 지점별 사용률, 연체 짐과 연체료

**본사 관리자**
- 정식 지점 등록·수정(주소 검색 → 좌표 자동 변환), 운영 신청 승인·반려, 문자·알림톡 발송 기록

## 예약 흐름

```
예약 ──(30분 안에 결제)──▶ 결제 완료 ──(시작일, 사장님 QR 스캔)──▶ 보관 중 ──(사장님 QR 스캔)──▶ 완료
  │                          │                                     │
  └─ 30분 지나면 자동 취소     ├─ 시작 전날까지 취소: 전액 환불          └─ 찾는 날이 지나면 연체 알림·연체료
     (EXPIRED)                ├─ 시작일 취소: 50% 환불
                              └─ 시작일에 안 오면 노쇼 (NO_SHOW)
```

보관 시작·종료는 이용자가 직접 바꿀 수 없고, **지점 사장님이 QR을 스캔해야만** 바뀝니다. 처음 버전에서는 이용자가 "픽업 완료"·"보관 완료" 버튼을 직접 눌렀는데, 그러면 실제로 짐을 맡겼는지 아무도 검증할 수 없다는 한계가 있어서 운영자 확인 흐름으로 바꿨습니다.

## 기술 스택

**Backend** — Java 17 · Spring Boot 4 · Spring Security (JWT + 리프레시 토큰) · Spring Data JPA · Flyway · PostgreSQL · Testcontainers
**Frontend** — React 19 · TypeScript · Vite · React Router · axios · qrcode / qr-scanner · 카카오 지도 SDK
**외부 연동** — 결제(PG) API · 솔라피(문자·카카오 알림톡) · Supabase Storage(S3 호환) · 다음 우편번호
**배포** — Supabase(PostgreSQL) · Render(Docker) · Vercel · GitHub Actions(CI, keep-awake)

## 기술적으로 눈여겨볼 부분

### 1. 동시 예약으로 정원이 넘치는 문제 — 비관적 락으로 해결하고 테스트로 증명
지점마다 하루 수용량이 있어서, 예약할 때 "기간 중 가장 붐비는 날의 짐 개수 + 새 짐 ≤ 수용량"을 확인합니다. 하지만 여러 요청이 동시에 들어오면 모두 같은 "남은 자리"를 보고 함께 저장해 버립니다.
- 예약을 만들 때 지점 행을 `SELECT ... FOR UPDATE`로 잠가서 같은 지점의 예약을 한 줄로 처리하게 했습니다.
- 실제 PostgreSQL 컨테이너에서 **수용량 5인 지점에 20명이 동시에 예약**하는 테스트를 만들었고, 정확히 5건만 성공합니다.
- **락을 빼고 같은 테스트를 돌리면 10건이 예약되는 것**(정원 2배 초과)을 확인해서, 락이 실제로 필요하다는 걸 증명했습니다.

### 2. 승인 처리에서 발생한 교착 상태(deadlock) 해결
같은 지점에 여러 사장님이 신청한 상태에서 관리자가 여러 신청을 동시에 승인하면, 한 명만 성공하고 나머지는 자동 반려돼야 합니다. 동시 승인 테스트를 돌려 보니 PostgreSQL이 **deadlock**을 감지했습니다.
- 원인: 각 요청이 "자기 신청 → 지점" 순서로 잠그고, 그다음 같은 지점의 다른 신청(다른 요청이 잠근 행)을 반려하려다 서로를 기다렸습니다.
- 해결: 락 순서를 항상 **지점 → 신청**으로 통일했습니다. 이후 5건 동시 승인에서 정확히 1건만 성공합니다.

### 3. 결제 마감과 결제 승인의 경쟁 상태
미결제 예약은 30분 뒤 스케줄러가 자동 취소하는데, 사용자가 결제창에서 결제하는 바로 그 순간에 취소되면 "돈은 나갔는데 예약은 없는" 상태가 될 수 있습니다.
- 결제 승인 직전에 예약 행을 잠그고 아직 결제 가능한 상태인지 다시 확인합니다. 이미 취소됐다면 **PG 승인 API를 아예 호출하지 않아서** 돈이 빠져나가지 않습니다(테스트로 검증).
- 결제창을 연 사람에게는 최소 10분을 보장하도록 마감 시각을 늘려 줍니다.

### 4. 휴대폰 인증과 로그인 유지
- 인증번호는 해시로만 저장하고, 재전송 60초·시간당 5회·입력 5회 제한으로 문자 비용과 무작위 대입을 막았습니다.
- 인증에 성공하면 **목적(가입/아이디 찾기/비밀번호 재설정/번호 변경)과 번호에 묶인 일회용 토큰**을 줘서, 인증과 실제 요청 사이에 번호를 바꿔치기하거나 가입용 인증으로 비밀번호를 바꾸는 걸 막습니다.
- 액세스 토큰(30분) + 리프레시 토큰(14일, 해시 저장·사용할 때마다 교체). **이미 교체된 토큰이 다시 오면 탈취로 보고 그 회원의 로그인을 모두 끊습니다.** 프론트는 만료 시 여러 요청이 동시에 실패해도 갱신을 한 번만 하도록 처리했습니다.

### 5. 알림은 트랜잭션이 커밋된 뒤에, 비동기로
문자 API를 예약 저장 트랜잭션 안에서 부르면, 저장이 롤백돼도 "예약 확정" 문자가 나가거나 문자 API가 느릴 때 요청 전체가 기다립니다. 알림은 트랜잭션 안에서 기록만 남기고 `@TransactionalEventListener(AFTER_COMMIT)` + `@Async`로 커밋 후에 보내며, 결과(발송/실패·사유)를 관리자 화면에서 볼 수 있습니다. 카카오 알림톡 템플릿이 승인된 알림만 알림톡으로, 나머지는 문자로 자동으로 나갑니다.

### 6. 스키마 관리와 DB 전환
- 개발 중 "재시작하면 회원 데이터가 사라진다"는 증상을 재현해서, `ddl-auto: update`가 데이터가 있는 테이블에 NOT NULL 컬럼을 추가하지 못하고 조용히 실패한다는 원인을 찾았고, 모든 스키마 변경을 Flyway 마이그레이션으로 옮겼습니다.
- 배포 DB를 Supabase(PostgreSQL)로 정하면서 MySQL·H2 전용 문법을 PostgreSQL로 옮기고, 테스트도 H2 대신 Testcontainers로 **배포와 같은 DB**에서 돌립니다.
- 배포 서버(UTC)에서 "오늘"이 어제가 되는 문제를 막기 위해 날짜 계산은 한국 시간 `Clock`으로 하고, 테스트에서는 고정된 `Clock`으로 환불·체크인 날짜 규칙을 검증합니다.

## 테스트

```bash
cd backend && ./gradlew test   # Docker 필요 (PostgreSQL 컨테이너)
```

70개 테스트 — 서비스 단위 테스트(요금·환불·수용량 규칙) + 실제 DB 통합 테스트(동시 예약·동시 승인, 결제→QR→체크인→체크아웃 전체 흐름, 자동 취소·노쇼·연체, 휴대폰 인증·리프레시 토큰, 역할별 접근 제어). GitHub Actions CI에서 푸시마다 실행됩니다.
